# Southbound review, October 2026

Three things in one document, as asked: a bug review of the whole repository, a scoping of red light
cameras in New York, New Jersey and Pennsylvania, and feature suggestions by category. It was written
against `main` at `9420bbd` (release v0.1.41, 11 October 2026).

**How to read it on a phone.** Section 1.1 is the short list that matters. Everything after it is
reference: per-module findings with file and line, test gaps, and what is already good. Sections 2
and 3 stand alone.

## 1. Bug review

### 1.0 How it was done, and what was not

Every Kotlin module, the Python and shell pipeline, the release gate and all seven workflows were read
in full, module by module, by nine parallel reviewers with the project's constraints in hand. Each
finding carries a severity, a file and line, a concrete failure scenario and a confidence:
**CONFIRMED** means the full code path was traced, **PLAUSIBLE** means the path is real but the
trigger depends on timing, data or a library's internals that are not in the repository. I re-read
the code for every High finding and for the security-relevant Mediums myself before including it.

What ran here: the pipeline's transit, routing, weather, regions and release-manifest unit tests, and
all 89 release-gate tests, all passing. What did not: the search pipeline tests need the pinned
`osmium` and `duckdb` wheels, and the Kotlin tests need an Android SDK, neither of which this review
environment has. CI runs both, so nothing below rests on a test I ran; it rests on reading.

One finding was dropped after verification. A reviewer reported that the Android Auto trip screen
would throw because its Stop action has no icon. The androidx source shows the navigation
template's action-strip constraints do not require icons (that rule belongs to the map action
strip), so the code is fine as written. It is mentioned so nobody chases it.

### 1.1 The findings that matter most

Ranked by how badly a driver would be hurt and how likely it is to happen. All six Highs are confirmed. All six are fixed in PR #54, each with a regression test where the logic is pure Kotlin.

**1. High. Opening a router deletes the routing-tile generation the updater is still filling.** *Fixed in PR #54.*
`core/packs/.../TileFolder.kt:64-69` (`prune`) deletes every generation that is not current or
in use, including an unfinished one, and `feature/explore/.../ExploreServices.kt:191` calls it
whenever a router opens. An update round begins generation N+1, hard-links the unchanged main-road
pack, then spends minutes downloading a changed region pack. The user asks for the first route of
the session: N+1 is deleted under the updater. `unpack` recreates the folder with only the new
tiles, `commit` writes a `packs.tsv` listing every pack and switches the pointer. Routing now has
no main-road tiles, and because the installed list equals the manifest every later round says
"up to date". Broken until upstream routing packs change. Fix: `prune` must skip generations
younger than the pointer or marked as being built, and the updater should hold a lock the router
opener respects.

**2. High. The closure reroute avoids the first 25 closures in the state, not the one ahead.** *Fixed in PR #54.*
`core/traffic/.../ClosureAvoidance.kt:59-60` (`polygons(List)`) takes the first 25 closures in
feed order, and its only caller, `feature/explore/.../ExploreMap.kt:679`, passes the whole
statewide list although it has just computed `ahead`. 511NY alone carried 209 closures on
7 October and sits first in the list. Driving in Pennsylvania, the app speaks "Road closed ahead,
finding another way", sends 25 New York squares to Valhalla, gets the same route back, and never
retries because the id is already in `announcedClosures`. The statewide list also replaces the
near-trip set in `nav.avoid` for the rest of the trip. Fix: pass `polygons(ahead)` merged with the
current `nav.avoid`.

**3. High. Closures on the opposite carriageway, or already behind the driver, trigger a reroute.** *Fixed in PR #54.*
`ClosureAvoidance.kt:63-64` (`onRoute`) ignores `Incident.direction`, unlike `PoliceAlerts`, and
`ExploreMap.kt:674` feeds it the full route geometry rather than the remaining route. Divided
carriageways are 10 to 30 m apart, inside the 50 m threshold. Northbound on I-87, a "I-87 Southbound:
Road closed" event 20 m away is spoken as a closure ahead and the 80 m exclusion square blocks both
directions, forcing a detour off an open road. Fix: use the heading test from `PoliceAlerts` and
the remaining geometry.

**4. High. Route preview crashes when the shorter-way probe returns the same route and there is only one option.** *Fixed in PR #54.*
`ExploreMap.kt:584-588` sets `shorterIndex` with `shorter?.takeIf { it in found }`, which is
structural equality on the uniffi `Route` data class. `ShorterRoute.merge` correctly refuses a
candidate that is not shorter and faster, but the candidate still equals the plain route, so with one
option `shorterIndex` is 0 and `RouteSummary.apartFrom(route, ranked[1])` throws
`IndexOutOfBoundsException` outside any `attempt`. With two or more options an alternate is
mislabelled "Shorter way". HANDOFF notes Shorter way is built but not yet driven, which is why it
has not been seen. Fix: set `shorterIndex` only when `found.size > avoided.size`.

**5. High. Transit planning fails for short trips with a zero-ride journey.** *Fixed in PR #54.*
`core/transit/.../Raptor.kt:137-148` can pick an access stop as the egress stop in round one
(origin and destination both within 800 m of the same stop), producing a journey with no rides;
`TransitPlanner.kt:157` then calls `rides.first()` and throws. The app's `attempt` swallows it and
shows "no trips", losing every ride option as well as the direct walk. Fix: skip zero-ride journeys
in `search`, or seed `target` with the direct walk.

**6. High. A map region arriving mid-trip orphans the running trip.** *Fixed in PR #54.*
`ExploreScreen.kt:106` rebuilds `ExploreMap` under `key(basemapGeneration, …)` on every basemap
install. The fresh map has no navigator and calls `openNavigator(navigating = false)`
(`ExploreMap.kt:295-298`), which closes the current router and builds a new idle navigator when
the tile generation changed (`ExploreServices.kt:186-199`). "Get for this trip" always adds a
region's tiles and the updater commits routing before maps, so: tap Get for a crossed region, start
driving, download finishes, the old Ferrostar core keeps speaking in its foreground service with a
closed router while the screen shows no overlay and no End button. Even without a tile change the
rebuild wipes `tripPlan`, the announced-incident sets and the dismissed faster-route (Medium, in the feature/explore
list below). Fix: `openNavigator` should detect navigation from its own navigator's state, and per-trip
state should live in `ExploreServices`.

**7. Medium. Update notifications never show on Android 12 and 12L.**
`core/updates/.../UpdateNotifications.kt:71` calls `context.checkSelfPermission(POST_NOTIFICATIONS)`
directly. On API 31 and 32 that permission does not exist and the platform answers DENIED;
`ContextCompat` exists to shim exactly this. With minSdk 31, the "tap to install" notification is
never posted on those versions and the update sits at `AwaitingInstall`. Fix: `ContextCompat` or an
SDK check.

**8. Medium. The weather workflow runs branch code with a write token.**
`.github/workflows/weather.yml:16,33,35` runs on every non-main branch push, with `contents: write`
and `GH_TOKEN` at job level, and executes `pipeline/weather/tests` and `forecast_pack.py` from the
pushed branch before the `PUBLISH` guard is consulted. A branch commit could `gh release upload
--clobber` an APK onto the published latest release. It breaks the rule release.yml keeps so
carefully ("no job with a write token runs repository code"). Fix: split publish into its own job
that checks out nothing, as release.yml does, or drop the write permission for branch pushes.

**9. Medium. A hand-pushed lower tag is published as latest.**
`release.yml:152-159, 804`: a tag push is never compared with the newest existing tag. Pushing
`v0.1.5` with `v0.1.60` present carries the packs over and marks `v0.1.5` latest, so Obtainium offers
a downgrade and the manifest's versionCode goes down. A part of 100 or more also collides in
`scripts/release-manifest.py:194` (`v0.1.100` becomes versionCode 200, the same as `v0.2.0`). Fix:
refuse a tag that does not sort above `previous`, and cap parts at 99 in the tag check.

**10. Medium. Turning street names off mangles traffic and weather alerts.**
`core/voice/.../GuidancePolicy.kt:158-168`: the `STREET_TAIL` regex's lazy match stops at the first
period, which in "Crash ahead on I 87 in 1.8 miles." is the decimal point. Result: "Crash ahead.8
miles."; "Snow on your route in 12 miles." becomes "Snow." The crash, roadwork, lanes and weather
templates all pass through this. Fix: exclude `TRAFFIC_ALERT` from the stripper, or match distances
first.

**11. Medium. A sentence already being synthesized plays after Mute or End.**
`core/voice/.../GuidanceVoice.kt:278-292`: mute, mute-until-next-turn and clear-queue only drop
waiting items and call `player.stop()`, a no-op while synthesis (0.5 to 3 s on Piper, up to 13 s on
system TTS) is still running; `play()` re-checks staleness afterwards but not the mute state. Fix:
re-check mute and trip state after synthesis.

**12. Medium. Camera-avoid exclusions apply to deviation reroutes from the live position.** *Fixed in PR #58.*
`core/routing/.../Navigator.kt:63,131,150,168`: `cameraAvoid` spots sit on the road beside each
camera and only the preview's waypoints get the 150 m clearance. A driver who misses the detour and is
on the excluded road has no usable origin edge, Valhalla finds no path, Ferrostar retries on each fix,
and `ExploreMap.kt:962` says "Rerouting." every second or two until the car passes the camera.
Plausible rather than confirmed (Valhalla's origin-edge behaviour is from memory). Fix: drop spots
within the clearance of the reroute origin.

**13. Medium. Search treats every state abbreviation but NY and NJ as a required word.**
`core/search/.../SearchQuery.kt:39` soft-matches only `ny, nj, usa, us`, while the packs now cover
seventeen more states and place text never carries the state. "Hartford CT" misses the city and
returns streets whose text contains "ct"; "Joe's Pizza Scranton PA" returns nothing. Fix: add the
covered states' abbreviations and names to the soft list.

**14. Medium. Curly apostrophes make names unsearchable.**
`pipeline/search/normalize.py:56` and `core/search/.../SearchText.kt:51` strip only the straight
apostrophe; U+2019 (what OSM editors type) becomes a space, so "McDonald's" indexes as "mcdonald s"
and the query "mcdonalds" finds nothing. A pipeline change, so it costs a data rebuild; land it with
the other pipeline fixes.

**15. Medium. First-use deadlock between search and restoring an Overture place.**
`core/search/.../SearchIndex.kt:36-38` versus `52-57`/`70-76`: `searchScored` holds the connection
lock then reads the lazy `hasOverture`; `place(id)` for an Overture id reads the lazy outside the lock
and its initializer takes the lock. Both block forever if they first run concurrently, which is
exactly the startup case. Fix: evaluate the lazies in the constructor.

**16. Medium. A style reload drops follow mode at sunset and sunrise.**
`core/map/.../SouthboundMap.kt:352-358` replays the last camera request on every style reload
(the effect is keyed on `style`), and the replay sets camera mode NONE, which dismisses tracking.
With night-by-sunset on, the preview's route-overview Fit is re-animated mid-drive and the map stops
following until the 10 s auto-recenter. Fix: remember the last applied request serial.

**17. Medium. A forecast pack that fails to parse is downloaded again every minute.**
`core/weather/.../WeatherFeed.kt:235-243`: the hourly throttle applies only once a forecast exists.
A future pack version or a truncated upload means a GitHub call and a 1 MB download every 60 s poll
while a place card or the weather layer is open; with no "weather" release at all, the API is hit
every minute from the shared unauthenticated quota. Fix: record the check time and the failed id
before parsing.

**18. Medium. The radar image is decoded on the main thread.**
`core/map/.../OverlayLayers.kt:315` decodes the 2400 by 1360 radar PNG (about 13 MB of pixels)
inside a `LaunchedEffect` on the UI thread every three minutes and on every style reload: a frame
stall of several hundred milliseconds while driving. Fix: decode on IO and hand the bitmap over.

**19. Medium. Resuming a kept import reverts places edited after the partial apply.**
`core/export/.../Backup.kt:155-177` with `AndroidBackupStores.kt:333` and the auto-resume in
`ExploreServices.kt:120-124`: an import that replaced places and keys but failed on a preference
write is retried at every start, and each retry re-applies the journal's places, deleting anything
saved since, with no notice. Fix: apply user data only if unchanged since the journal was written, or
tell the user before resuming.

**20. Medium. Expired, scheduled, resolved and ramp closures are treated as live road closures.**
Four related readers in `core/traffic`: `NorthDakota.kt:56-75` never reads `EffectiveUntil` (the
real fixture's rows had expired months before), `TravelMidwest.kt:93-113` ignores the `a` (active)
flag its own comment describes, `MarylandChart.kt:49` reads CHART's lifecycle `closed` flag as a road
closure, and `CarsStates.kt:160`, `TravelMidwest.kt:123-124`, `FiveElevenNy.kt:93`,
`FiveElevenNyCars.kt:105` make any "ramp closed" event a mainline closure whose square sits at the
gore on the interstate. Each yields a spoken closure and an exclusion square on an open road. The
first two are confirmed from fixtures; the CHART one needs a single probe run.

**21. Medium. Two update rounds can run at once and share a download path.**
`core/updates/.../UpdateScheduler.kt:162-205` keeps NOW and DAILY as separate unique works with no
lock; both write `packs/download/<name>.part` and both open a tile generation. One truncates the
other's half-written file, the digest is taken from the network stream so it passes, and a file
with a hole is renamed into place under the manifest's hash. Plausible, timing-dependent.

**22. Medium. A manifest with no routing packs deletes the phone's offline routing.**
`Updater.kt:96-101,120-129` with `scripts/release-manifest.py:71-74`: if `routing-packs.json` is
missing from a release the script silently lists no routing tars; the app sees an empty routing set
as a change, commits an empty generation, prunes the good one and deletes `routing-nys.tar`. One
packaging slip breaks the offline hard constraint. Fix: refuse an empty routing list in both places.

**23. Medium. Settings changes made just before Back can be lost, and the speech-rate slider truncates.**
`feature/settings/.../SettingsScreen.kt:95-98, 232-237` launches every DataStore write in the
composable's scope, which is cancelled on Back while a slider drag's queued writes are still
pending; and `:234` truncates `(r * 10).toInt() / 10f`, so tick values that land at 1.1999 store
1.1 and some widths cannot select 1.2 or 1.9. Fix: an application scope or `NonCancellable`, and
`roundToInt()`.

**24. Medium. Empty inputs ship silently as packs.**
`pipeline/search/build.sh:186-195` and `dot_cameras.py:234-255` build a pack with zero DOT cameras
when a state's feed changes shape or fails, with no warning on a zero count;
`addresses.py:171-181` and `overture.py:277` likewise contribute zero rows if a column is renamed.
"Avoid DOT cameras" then does nothing until the next monthly rebuild. Fix: a minimum-row guard per
source that fails the build or at least annotates the run.

**25. Medium. The daily update job can never finish a multi-gigabyte download.**
`UpdateWorker.kt:307-309` with `UpdateScheduler.kt:162-168`: the daily work is not expedited, and on
Android 12+ `setForeground()` from a background-started worker throws (swallowed), so the round runs
under WorkManager's 10-minute cap, is cancelled, re-enqueued and restarted from byte zero. Plausible;
it would show as downloads that never complete overnight.

**26. Medium. The arrival card never shows on the early-arrival path.** *Fixed in PR #58.*
`feature/explore/.../GuidanceSupport.kt:213` ends the trip while Ferrostar is still Navigating
(within 25 m with a poor fix), so the state goes Navigating to Idle, never Complete, and the card
with side-of-street and parking is skipped in exactly the between-buildings case it was written for.

### 1.2 Suggested order of fixes

Grouped so pipeline changes, which each cost a data rebuild, land together.

1. **App, driving safety (one PR):** items 12 and 26 and the explore Lows that touch the trip, now that
   items 1 to 6 are fixed in PR #54. These are the ones that could still strand a driver. *Done in PR #58*:
   with the per-trip state the map rebuild wiped, the Navigator's unguarded `replaceRoute`, the late
   faster-route accept, the reroute exception handling, the mute lift on a reroute, Resume and Start here,
   the waiting preview's Back, the start region in `missingRegions` and stale last-known fixes. The
   24-hour arrival clock and the frozen preview clock go with the polish group.
2. **App, data integrity (one PR):** items 7, 15, 19, 21, 22, 25 plus the update Lows.
3. **App, polish (one PR):** items 10, 11, 13, 16, 17, 18, 23 and the voice and settings Lows.
4. **Workflows (one PR, no rebuild):** items 8 and 9, the `data.yml` checkout pin, the stray-tag guard.
5. **Pipeline (one PR, one rebuild):** items 14 and 24, the red light camera sub-tags from section 2,
   the school-zone precedence, the transfer grid, the split-tile edge rule, and a U+2019 case in
   `normalize_cases.json` so the Kotlin twin is tested too.
6. **Traffic readers (one PR):** item 20 after a probe run confirms the CHART and NDDOT semantics.

### 1.5 What is in good shape

It is worth saying plainly, because the list above is long. The privacy architecture holds
everywhere it was checked: one gated door for the network, per-feature toggles read by both the UI
and the gate, every feed URL a compile-time constant or derived from feed content, the API key
confined to its own host's query string and stripped from error messages, GPS only from
`LocationManager`, and nothing about the route or the search in any request. Pack downloads verify
byte count and SHA-256 over the stream, confirm the kind by content magic, and switch by atomic
rename; APK updates check checksum, package, version code and signer lineage. The backup format is a
careful verify-then-commit design with strict JSON and a hash-pinned codec. The release pipeline is
unusually disciplined for a one-person project: digest-pinned containers with a test guarding the
pins, hash-locked pip, a signing job that runs no repository code, the certificate checked against
the baseline before anything is uploaded, and a gate that decodes the manifest itself and fails
closed. The pure logic (guidance policy, speech queue, RAPTOR, route alerts, camera avoidance,
opening hours, normalisation shared with the pipeline through fixture files) is tested with
hand-drawn cases that pin real behaviour. The bugs above are mostly at the seams between these
well-built parts, which is where a second pair of eyes earns its keep.

### 2.2 Where the data could come from

Southbound's rule is that nothing about the trip leaves the phone, so red light cameras must ride in
the search pack like speed cameras, plate readers and DOT cameras do today. Four candidate sources,
in order of quality:

1. **Official open datasets.** Philadelphia and Chicago publish coordinates. These are the only
   sources that are complete, machine-readable and refreshed. A `red_light_cameras.py` sibling of
   `pipeline/search/dot_cameras.py` would fetch them at build time with the same "a state that fails
   is left out, never the pack" rule.
2. **Official intersection lists without coordinates** (Yonkers, White Plains, New Rochelle, the
   Bucks and Montgomery townships, Pittsburgh's releases). Tens of points that change a few times a
   year. The honest way to ship them is a hand-kept GeoJSON in the repository
   (`pipeline/search/red_light/<state>.geojson`), each point with its source URL and the date it was
   checked, and a pipeline test that every point lies inside its municipality. Geocoding "Main St &
   MLK Blvd" automatically against the pack's own street index is possible (both ways are in the
   pack) but is a project in itself and fails silently on renamed streets.
3. **OpenStreetMap.** There is no settled tag for the device. The documented scheme is a relation
   `type=enforcement` + `enforcement=traffic_signals` with the signal node as a member; the device
   node is most often tagged `highway=speed_camera` (sometimes with `speed_camera=traffic_signals`),
   and `highway=red_light_camera` had only 31 uses worldwide in 2021
   ([OSM tagging list](https://lists.openstreetmap.org/pipermail/tagging/2021-December/063338.html),
   [OSM wiki](https://wiki.openstreetmap.org/wiki/Traffic_enforcement)). Two consequences for this
   repository:
   - **Today's pipeline already mislabels some red light cameras as speed cameras.** `landmark_category`
     in `pipeline/search/build_search.py` maps every `highway=speed_camera` to `speed_camera`, so a
     red light camera tagged the common way is announced as "Speed camera ahead". Reading
     `speed_camera=traffic_signals` and `enforcement=traffic_signals` on the node is a two-line fix.
   - The handler reads nodes and ways only (`.with_locations()`, no `relation` callback), so the
     relation scheme is invisible to it. Supporting it needs a relation callback that resolves the
     `device` (or, failing that, `to`) member's node location, which with pyosmium means a first pass
     collecting member node IDs or an `idx` location store.
   - Counts for NY/NJ/PA could not be measured from this session (the Overpass and taginfo hosts
     are not reachable from the review container); `.github/workflows/feed-probe.yml` runs on
     GitHub's runners and is the right place to count before deciding how much OSM contributes.
4. **Derived from violation data.** NYC's "Open Parking and Camera Violations" dataset (nc67-uf89)
   records every "FAILURE TO STOP AT RED LIGHT" ticket with a recorded location string, and a
   third-party tool already groups them by location and month
   ([reports.jehiah.cz](https://reports.jehiah.cz/red_light/)). Clustering that text gives an
   approximate map of NYC's active cameras that DOT itself will not publish. It is weekly, large,
   needs geocoding against the NYC street index, and lags new cameras by a billing cycle. It is the
   only route to NYC coverage; it should be labelled "approximate, from ticket data" wherever it
   shows.

Commercial databases (Waze, SCDB, Trapster's successors) are off the table: their terms forbid
redistribution and they would taint the open packs.

### 2.3 How it would fit the app

Everything below reuses what plate readers and speed cameras already have, so the new code is small.

- **Pack:** a new `landmark.category` value `red_light_camera`. The app only asks for categories by
  name, so an older app with a newer pack ignores the rows and a newer app with an older pack gets
  none. No schema bump is needed; `direction` can carry the enforced approach where a source gives
  one (Chicago does; the townships do not).
- **Guidance:** `AlertKind.RED_LIGHT_CAMERA` in `core/search/RouteAlerts.kt`, a
  `redLightCameraAlerts` toggle in `VoiceSettings` (which, per the export rules, bumps the backup
  bundle schema from 6 to 7), a string "Red light camera ahead" wired in `GuidanceSupport`, and a
  map dot. The route card's exposure line grows a fourth part ("2 red light cameras").
- **No avoidance.** Routing around a camera at a signal means routing around the intersection, which
  rarely has a sane alternative, and the honest driver has nothing to gain. Counting and announcing
  is the right scope.
- **Direction matters more than for speed cameras.** A red light camera enforces one or two
  approaches of an intersection. Where the source gives approaches, use `RouteAlerts.faces` as it
  already does for plate readers; where it does not, announce on every approach and say so in
  Settings.
- **Coverage.kt** gets an item `RED_LIGHT_CAMERAS`: New York *partial* ("New York City keeps its 600
  locations secret; Nassau publishes none; Yonkers, White Plains and New Rochelle publish theirs"),
  New Jersey *none* ("none by law since December 2014"), Pennsylvania *partial* ("Philadelphia's
  official list; Pittsburgh and the Bucks and Montgomery townships from their announcements"). The
  existing `CoverageTest` pattern (the pipeline's list of states checked against the phone's) extends
  naturally.
- **Legality of warning the driver:** warning apps for fixed cameras are lawful in all three states;
  Waze and the car makers' built-in navigation have done it for years. New York's restriction on
  windshield-mounted devices is about obstruction, not warnings.

### 2.4 Recommendation

Do it in two steps. First, the cheap and certain part: read the OSM sub-tags so existing red light
cameras stop being called speed cameras, add the `red_light_camera` category, alert and count, and
ship Philadelphia's dataset plus a hand-kept GeoJSON for the ten or so New York and Pennsylvania
municipalities that publish lists. That covers everything that is publicly knowable and is roughly
the size of the DOT-cameras change. Second, decide whether NYC's 600 secret intersections are worth
the violation-data derivation; it is the only way to cover the one place with the most cameras, and
it is a week of pipeline work with an "approximate" label attached forever. Watch two dates: New
Jersey's next session (any reauthorization would reopen the question there) and Pennsylvania's
15 July 2027 sunset (if it lapses, every Pennsylvania row is removed by the monthly rebuild).

### 2.5 Decision (owner, 12 October 2026)

The owner asked whether the publicly known set was too small to be worth a build. In New York, New Jersey
and Pennsylvania it is: about 100 intersections can be located, while New York City's 600, Nassau's up to
100 and Albany's 20 or so are unpublished. Across all the states the app covers it is larger, because
Chicago (about 150 intersections) and DC (every automated camera, CC BY 4.0) publish theirs as open data.

Decided: **open data only.** Read OSM's red light sub-tags so those cameras stop being announced as speed
cameras; add the `red_light_camera` category with its alert and count; load Philadelphia's, Chicago's and
DC's datasets at each monthly data rebuild, as `dot_cameras.py` does for DOT cameras (DC's speed and stop
sign cameras come with it). Philadelphia's and Chicago's terms of use are checked before their rows ship.
No hand-kept lists, and no estimate of New York City's sites from ticket data.

   `turn:lanes`; a dedicated lane strip above the banner for the last 500 m before an exit is the
   single biggest readability gain on highways.
3. **Parking at the destination.** The arrival card already says whether parking is listed nearby;
   go one step further with a "Park here" button that routes to the nearest `amenity=parking` with
   capacity and fee tags, then switches to walking for the last stretch.
4. **Trip history on the phone.** Encrypted, local, exportable through the existing backup: start,
   end, distance, duration, cameras passed. Useful for mileage logs and for the owner's own testing;
   never leaves the phone.
5. **Elevation** (*planned*): grades in the routing tiles make Avoid hills real for bikes and let the
   RV profile warn on long descents.
6. **Speed-trap style "Report" that stays local.** A long-press on the map during navigation drops a
   private marker (camera, hazard, police) that is announced on later trips. No upload, no sharing,
   so it fits the privacy rules and still gives the owner a way to mark cameras OSM lacks.
7. **Offline EV charging along the route.** The place categories in `build_search.py` have
   `amenity=fuel` but not `amenity=charging_station`; adding it (with the `socket:*` and `capacity`
   tags as the description) and a "Charge along the way" filter on the route preview, like gas
   stations, is mostly pack and UI work.

### 3.3 Search and places

Builds on: FTS5 trigram search, NYS Address Points, Overture places (NY and northern NJ), opening
hours, Home and Work chips.

1. **Overture places for the other eighteen states.** Measured at about 480 MB for New York; the
   README already tells users that search is thinner outside New York. Shipping it per region keeps
   each pack small.
2. **Category browsing without typing:** "Gas", "Food", "Coffee", "Pharmacy", "EV charging" chips
   under the search box, each a `nearby()` query the index already supports, ranked by detour from
   the active route while navigating.
3. **Address interpolation** for house numbers between known points, from OSM `addr:interpolation`
   ways and the state address files, so "412 Main St" lands on the right block when only 400 and
   420 are mapped.
4. **Coordinate entry and sharing:** paste or type `40.7128, -74.0060` or a `geo:` URI and get
   a pin; share a place as a `geo:` URI. Zero network. The manifest's VIEW filter takes only
   `content:` URIs with pack MIME types today, so a `geo:` filter is a new entry (and a gate
   baseline change).
5. **Addresses from the National Address Database.** USDOT's NAD is public domain (release 19,
   about 90 million records, refreshed in 2026) and aggregates the states' own address points, so one
   loader covers whichever of the nineteen states take part, to match New York's address quality
   ([transportation.gov/nad](https://www.transportation.gov/nad)).

### 3.4 Transit

Builds on: NYC subway, bus, LIRR and Metro-North RAPTOR planning, departure boards, MTA realtime
behind toggles.

1. **NJ Transit, PATH, SEPTA, CTtransit, Shore Line East, MARC and WMATA GTFS** in the transit pack,
   one agency per sub-table, so the trip planner works on both sides of the Hudson and down the
   corridor. The builder is MTA-specific today (*planned* as "upstate transit"), so generalizing it
   is the enabling step.
2. **Upstate systems** (CDTA, NFTA, RTS, Centro) (*planned*).
3. **Realtime for the new agencies** behind the same per-feature toggles, fetched whole per agency
   (GTFS-RT TripUpdates are small).
4. **Park and ride suggestions:** a drive-to-station then train plan when driving all the way into
   Manhattan would be slower, using the routing engine for the first leg and RAPTOR for the second.
5. **Service alerts spoken** when a planned trip's line has an alert, through the existing
   transit-stop alert channel.

### 3.5 Live data, weather and hazards

Builds on: 511 feeds in sixteen states, NYC DOT speeds, cameras and message signs, NWS alerts and
radar, forecast pack, gas prices.

1. **Road weather (RWIS) sensors** from the states that publish them (511PA, Mi Drive, 511MN, SD511
   already ship RWIS points next to their cameras): pavement temperature and "slippery" flags are
   worth a spoken warning in winter.
2. **Winter road conditions** layers (Minnesota, Iowa, the Dakotas, Nebraska and Kansas publish
   plowed/partially-covered/closed segments) drawn like NYC DOT speeds and factored into the
   "+X min" estimate.
3. **New Jersey traffic via a different door.** 511NJ refuses GitHub's runners; the phone fetching
   it directly would still carry no location (whole-state feed), so it fits the rules if the
   feed-probe ever finds a stable endpoint. Worth one probe a quarter.
4. **Feed freshness in the UI:** every feed row already carries an `updatedAt`; show the newest one
   on the traffic button and say "Traffic is 40 minutes old" when stale, as the NYC DOT layer alone
   does today.
5. **Air quality** from AirNow's whole-state files (no key, no location) as a one-line note on the
   weather card. Low effort, small value, but often asked for.

### 3.6 Privacy, security and trust

Builds on: NetworkGate with per-feature toggles, encrypted keys and user data, passphrase-sealed
export, release gate, reproducible pipeline, pinned actions.

1. **A visible network log.** Settings > Live data could show the last 50 requests the gate made:
   host, feature, bytes, time, and nothing else. It turns the privacy promise into something the
   owner can check on the phone and is the best possible answer to "what does this app send".
2. **Certificate pinning for GitHub downloads** (or at least a pinned set of CAs) so a hostile
   network cannot swap the release manifest; the SHA-256 check already protects pack contents, but
   the manifest itself is trusted on first fetch.
3. **Reproducible APK builds** so a user can rebuild the release and compare the signing input; the
   gate already compares the APK against a baseline, so publishing the build's inputs and a diff
   script is the remaining step.
4. **Duress and lock options:** a setting to require the phone's lock before opening saved places
   and recents (BiometricPrompt with the Keystore key), and "clear recents when the trip ends".
5. **Dependency and action update cadence:** a monthly Dependabot or Renovate run that opens one PR
   with the `verification-metadata.xml` regenerated by CI, so pins do not rot.

### 3.7 Data, packs and updates

Builds on: regional packs, SHA-256 manifest, split routing packs, Get for this trip, APK
self-update, monthly data rebuild.

1. **Delta updates for search packs.** The monthly rebuild changes a few percent of rows; shipping a
   SQLite session changeset or an rsync-style delta would cut a 200 MB download to tens of MB on
   mobile data.
2. **Storage view:** a per-region size breakdown (map, search, directions) with "remove" buttons and
   a total, so a 64 GB phone owner can see where 6 GB went.
3. **Pack age and provenance on the phone:** the OSM extract date and the state address file date per
   pack, shown in Settings and in About, so "the map is wrong here" has a date to pin on.
4. **Scheduled downloads:** "update only between 1 and 5 am on Wi-Fi while charging", through
   WorkManager constraints the updater mostly has already.
5. **Smaller routing seam packs:** several `routing-*-*.tar` files in the release are under 1 MB;
   folding them into their neighbours cuts the manifest and the request count.

### 3.8 Interface and accessibility

Builds on: Compose UI, landscape driving layout, night mode, haptic turns, voice modes.

1. **Large-type and high-contrast navigation mode** for older eyes on a dash mount: one toggle that
   scales the banner, arrival card and speed limit, independent of the system font size.
2. **Glanceable widget** with the next departure from the nearest saved stop or the drive time to
   Work, computed on the phone from the packs; no network.
3. **One-handed layout:** the search box and the route options reachable from the bottom third of
   the screen on tall phones.
4. **Voice input for the search box** using the system speech recognizer only when it is on-device
   (Android reports `isOnDeviceRecognitionAvailable`), otherwise hidden, to stay within the rules.
5. **TalkBack pass** on the route options and the camera-exposure line: 33 icons in the feature
   modules pass a null content description, which is right for decoration beside text but wrong for
   the ones that are the only label (the voice button's mode, the re-center pill).

### 3.9 Pipeline, quality and operations

Builds on: pyosmium and DuckDB builders, pinned containers, pipeline unit tests, release gate,
feed-probe workflow, pyvalhalla route checks.

1. **On-device crash log viewer with "copy to clipboard".** Crash SDKs are banned, so the only way to
   get a stack trace from the owner's phone is to catch it in-process, store it locally, and let them
   paste it into a GitHub issue. One screen, high leverage for a one-phone project.
2. **Screenshot tests for the navigation screen** in CI (Compose's `captureToImage` on a Robolectric
   graphics-enabled run) so layout regressions show up in the pull request, not on the drive.
3. **Golden-route regression tests** on each data rebuild: a dozen owner-chosen trips whose distance,
   duration and camera counts are compared with the previous release and reported in the release
   notes, so a bad OSM edit or a routing-pack split bug is visible before the APK is installed.
4. **A feed health badge in the README** from the weekly feed probe (which states answered, which
   went dark), the same information the app shows under What each state has.
5. **A `make -C pipeline nyc` smoke run on every pipeline pull request** that also runs the app's
   JVM tests against the fresh pack, since the pack schema and the Kotlin readers drift
   independently today.
